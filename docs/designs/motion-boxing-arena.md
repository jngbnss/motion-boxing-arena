## Problem Statement

웹캠 하나로 사용자의 실제 복싱 동작(펀치·가드·회피)을 인식해, 사용자가 2D 그림으로 만든 3D 캐릭터가
1인칭 시점에서 AI 또는 원격 상대와 복싱하는 웹 게임을 8주, 7명 팀으로 만든다.

## What Makes This Cool

- "내가 그린 낙서가 내 주먹으로 싸운다." 그림 → 3D → 내 몸으로 조종이라는 3단 변신이 한 화면에서 이어진다.
- 상대의 펀치를 **실제로 고개를 젖혀 피하는** 순간이 핵심 "whoa" 포인트다. 버튼이 아니라 몸이 입력이다.
- 시연 트릭: 캐릭터 생성을 **캘리브레이션 전에 걸어두고 AI와 한 판 하는 동안** 생성이 끝나 재대결에서 내 캐릭터가 등장한다. 생성 대기시간이 연출이 된다. 시간 조건과 미완료 시 처리는 C13에 있다.

## Constraints

- 8주, 7명(프론트/디자인 + AI/백엔드/3D 혼합). 역할은 조정 가능.
- 브라우저 실행, Windows 개발 환경, 무료·저비용 배포 우선.
- 단일 RGB 웹캠. 깊이·힘 측정 불가 전제.
- 팀 소재지 대한민국 → **라이선스 지역 제한 모델 사용 불가** (아래 Premise 5).
- 홀로그램은 MVP 범위 밖. 렌더 출력 인터페이스만 예약.

## Premises (자동 동의)

1. **핵심 시연 경로가 생명선이다.** 캐릭터 선택 → 웹캠 인식 → 1인칭 복싱 → 회피 → 타격/승패. 2D→3D와 온라인 대전은 "시연 범위 조정 가능" 기능이다. 이 둘이 실패해도 시연은 성립해야 한다.
2. **모션 인식은 "아바타 미러링"이 아니라 "행동 이벤트 생성기"다.** MediaPipe 출력은 `jab`, `straight`, `guard`, `slip_left` 같은 이벤트와 저차원 연속값(머리 오프셋, 가드 가중치)으로 압축된다. 게임 캐릭터의 팔 궤적은 게임 애니메이션이 만든다.
3. **타격 판정은 실제 팔 길이·거리와 무관하다.** 실제 펀치는 "트리거"일 뿐이고, 사거리와 궤적은 게임 규칙이 정한다. 충돌 볼륨은 메쉬가 아니라 **공통 스켈레톤의 정규화된 히트 볼륨**으로 정의한다(거대 로봇도 히트박스는 동일 → 공정성).
4. **공통 스켈레톤(`mba-humanoid-v1`) 하나로 모든 캐릭터를 움직인다.** 캐릭터마다 다른 스켈레톤은 지원하지 않는다(요구사항 10의 B안).
5. **Hunyuan3D 계열은 사용하지 않는다.** Tencent Hunyuan 3D Community License(2.1 기준)는 Territory에서 EU·UK·**South Korea를 제외**하고, Territory 밖 사용은 라이선스 없음으로 규정한다. 출처: https://huggingface.co/tencent/Hunyuan3D-2.1/blob/main/LICENSE
6. **MVP는 추가 학습 없이 구현한다.** 학습이 필요한 부분은 "수집 데이터로 규칙 기반 대비 개선이 입증될 때"만 진행한다.
7. **원본 웹캠 영상은 어디에도 전송·저장하지 않는다.** 추론은 브라우저 로컬. 네트워크에는 행동 이벤트와 저주기 상태만 전송.
8. **LLM은 쓰지 않는다.** 게임 AI는 FSM. 학습된 모델이 필요한 곳은 포즈 추정, 배경 제거, 이미지→3D, (선택) 자동 리깅뿐이다.

## Approaches Considered (2D→3D 캐릭터, 요구사항 4의 A/B 비교 포함)

### Approach A: 완전 자동 생성 + 자동 리깅 (요구사항의 "방식 A")
이미지 → 3D 메쉬 → 신경망 자동 리거(UniRig/Puppeteer)가 캐릭터별 스켈레톤 생성 → 캐릭터별 애니메이션 리타겟.
- Effort XL / Risk High. 자유도 최고, 비인간형도 이론상 가능.
- 스켈레톤이 캐릭터마다 달라 복싱 애니메이션 재사용·판정 일관성이 무너진다. 8주 내 성공 가능성 낮음.

### Approach B: 공통 스켈레톤 + AI 외형 (요구사항의 "방식 B") ← **채택**
이미지 → 3D 메쉬 → 정규화 → **공통 스켈레톤 `mba-humanoid-v1`에 바인딩** → 공유 애니메이션 라이브러리 재사용.
바인딩은 두 전략을 자동 선택한다:
- **Smooth bind**: Make-It-Animatable(MIT, 휴머노이드/Mixamo 계열 학습) 또는 Blender 자동 가중치. 사람형·만화형에 적합.
- **Rigid bind**: 메쉬를 뼈 근접도로 분할해 각 조각을 한 뼈에 100% 가중치로 붙임. 로봇·장난감형에 오히려 자연스럽다. 단, 메쉬-스켈레톤 정렬(C14)이 성공해야만 가능하며 정렬에 실패하면 T0로 간다.
- 검증기(C14: 테스트 포즈 6종의 엣지 늘어남 비율·뒤집힌 삼각형)가 smooth 실패 시 rigid로 자동 강등한다. rigid 결과도 테스트 포즈에서 조각 간 관통 깊이 ≤ 3cm(초기값)를 검사하고, 실패하면 T0로 간다.
- Effort L / Risk Med. 애니메이션·판정·네트워크가 캐릭터와 무관하게 동작.

### Approach C: 스킨 모드 (항상 성공하는 최종 대체 경로)
3D 생성 없이, 업로드 이미지에서 **팔레트 추출 + 데칼(가슴/트렁크/글러브/얼굴판)** 을 기본 복서에 입힌다. 클라이언트에서 2초 내 완료.
- Effort S / Risk Low. 생성 실패·GPU 부재·시간 초과 시 즉시 제공.

## Recommended Approach

**B를 주 경로로, C를 보장 경로로.** 생성 품질 단계는 다음 3단계로 사용자에게 제시된다.

| Tier | 이름 | 조건 | 결과 |
|---|---|---|---|
| T2 | Full 3D (smooth) | 휴머노이드 판정 + smooth 검증 통과 | AI 메쉬 + 부드러운 관절 |
| T1 | Full 3D (rigid) | 정렬·휴머노이드 판정 통과 + smooth 검증 실패 | AI 메쉬 조각 + 강체 관절(액션 피규어 느낌) |
| T0 | Skin | **업로드 즉시 항상 생성**. 정렬 실패/생성 실패/타임아웃/GPU 없음 시 최종 결과 | 기본 복서 + 이미지 기반 색·데칼 |

이미지→3D 모델은 **W1~W2 PoC 벤치마크로 결정**한다. P2 PoC는 Open Question 1(GPU 확보)이 W1 Day1에 답해져야 시작할 수 있다. 후보(확인된 범위에서 지역 제한 없음. "추정" 항목은 원문 확인 필요):

| 후보 | 라이선스 | VRAM | 속도 | 역할 |
|---|---|---|---|---|
| TRELLIS.2 (Microsoft) | MIT (단, nvdiffrast 등 의존성은 NVIDIA 별도 라이선스 → 비상업 프로젝트에서 사용, 확인 필요) | 24GB+ | H100 기준 3~60초 | 품질 1순위 후보 |
| TRELLIS (v1) | MIT (추정, 확인 필요) | 약 16GB (추정) | 수십 초 (추정) | 24GB GPU 없을 때 |
| SPAR3D / SF3D (Stability) | Stability Community License (연매출 100만 달러 미만 무료) | 명시 없음 | 1초 미만 | 속도 1순위 후보 |
| TripoSR | MIT (추정) | 약 6GB (추정) | 1초 미만 | 저사양 베이스라인 |
| Meshy API (유료) | 상용 약관 | 없음 | 수십 초~분 (추정) | GPU 확보 실패 시 대체. 리깅·애니메이션 API 포함 |

### C2. 행동 이벤트 (motion → game)
```ts
type Hand = 'lead' | 'rear';               // 오소독스: lead=왼손, rear=오른손 (사우스포 설정 시 반전)
type StrikeType = 'jab' | 'straight' | 'hook' | 'uppercut';   // MVP: jab, straight
type DefenseState = 'none' | 'guard' | 'slip_left' | 'slip_right' | 'duck';  // MVP: none, guard, slip_*
interface StrikeEvent { kind: 'strike'; type: StrikeType; hand: Hand; t: number; confidence: number; seq: number; }
interface PoseState  { headX: number; headY: number; guard: number; t: number; }  // headX/Y: 캘리브레이션 기준 정규화(-1..1), guard: 0..1
```

### C3. 공통 스켈레톤 `mba-humanoid-v1`
Mixamo 명명 호환 22본 부분집합: `Hips, Spine, Spine1, Spine2, Neck, Head, {Left,Right}Shoulder, {L,R}Arm, {L,R}ForeArm, {L,R}Hand, {L,R}UpLeg, {L,R}Leg, {L,R}Foot, {L,R}ToeBase`.
레스트 포즈 A-pose(팔 45°), 키 1.8m 정규화, +Y up, glTF 정면 +Z.
히트 볼륨은 스켈레톤 기준 정규값(머리 구 r=0.13m, 몸통 캡슐 r=0.18m h=0.5m, 글러브 구 r=0.08m)이며 캐릭터 메쉬와 무관.

### C4. 아바타 인터페이스 (클라이언트)
```ts
interface BoxerAvatar {
  readonly manifest: CharacterManifest;
  load(): Promise<void>;
  play(action: AvatarAction, opts?: { speed?: number }): void;   // idle, jab_lead, straight_rear, guard, hit_head, hit_body, ko, ...
  setHeadOffset(x: number, y: number): void;   // 시각 표현 전용(감쇠 적용). 판정에 쓰지 않음
  setGuardWeight(w: number): void;
  getHitVolumes(): HitVolumes;                 // 디버그 표시용 정규 볼륨. 실제 판정은 packages/combat가 비감쇠 PoseState로 계산(C11)
  update(dt: number): void;
  dispose(): void;
}
```

### C5. 캐릭터 매니페스트 `character.json`
`id, name, ownerId, skeleton:'mba-humanoid-v1', tier:'T0'|'T1'|'T2', glbUrl, thumbnailUrl, skin?:{palette, decals}, scale, provenance:{model, modelVersion, seed, rigger, createdAt}, license:{userAttestedRights:boolean, visibility:'private'}` (MVP는 `private`만. `unlisted`/`public`은 확장, C16)

### C6. 전투 타임라인 (packages/combat 상수, 튜닝 대상)
| 기술 | startup | active | recovery | 데미지(머리/몸통) | 가드 시 |
|---|---|---|---|---|---|
| jab | 100ms | 80ms | 200ms | 6 / 4 | 20% 칩 |
| straight | 160ms | 100ms | 300ms | 12 / 8 | 20% 칩 |
- HP 100, 피격 경직 300ms, 손별 쿨다운(recovery 종료까지 재입력 무시), 초당 최대 4펀치.
- 판정 시점 = active 시작 시점의 **방어자 상태**(머리 오프셋/가드). 회피는 "히트 구가 이동한 머리 구와 교차하지 않음"으로 계산.
- 라운드: MVP 1라운드 90초, HP 0 → KO, 시간 종료 → 남은 HP 비율 판정.

### C7. 실시간 이벤트 (Colyseus 메시지 + 상태 스키마)
클라→서버: `room:ready`, `calib:done`, `input:strike`(C2), `input:pose`(C2, 20Hz), `player:character`(C13), `match:rematch`
서버→클라: 상태 동기화(Colyseus Schema: phase, players[hp, connected, ready, calibrated, characterId], timer) + 이벤트 `match:countdown`, `match:start`, `combat:strike_start`, `combat:hit`, `combat:blocked`, `combat:dodged`, `strike:rejected`(C17), `match:paused`, `match:resumed`, `match:end`.
서버 권한: 데미지·HP·승패·쿨다운은 서버만 결정. 클라는 자기 펀치 애니메이션만 즉시 재생(예측).

### C8. 게임 단계 상태 머신
`LOBBY → WAITING_OPPONENT → CALIBRATING → READY → COUNTDOWN(3s) → FIGHTING ⇄ PAUSED → KO | TIME_UP | FORFEIT → RESULT → (REMATCH → CALIBRATING 생략 READY)`
PAUSED 사유: ① 연결 끊김(재접속 대기 ≤ 20s) ② 추적 손실(C12, 싱글 2s / 온라인 3s 후 진입, 누적 예산 30s) ③ 사용자 일시정지(싱글). 재개 시 3초 카운트다운 후 FIGHTING.

### C9. AI 생성 작업 상태
`QUEUED → PREPROCESSING → GENERATING → POSTPROCESSING → RIGGING → VALIDATING → EXPORTING → READY`
실패 시 `FAILED{stage, retryable, reason}`. 각 단계 산출물은 오브젝트 스토리지에 저장, 재시도는 실패 단계부터.
큐는 **Postgres 테이블 + `SELECT … FOR UPDATE SKIP LOCKED`** (Redis/Celery 미사용).

### C10. 회피 가능 시간 창 (Dodge Window) — 핵심 "whoa"의 성립 조건
사람의 시각 반응(약 200~250ms)과 입력 파이프라인 지연(p50 목표 150ms)의 합은 약 350~400ms다. jab startup 100ms로는 **반응형 회피가 불가능**하므로 모드별로 규칙을 나눈다.

| 모드 | 회피 가능 창 | 규칙 |
|---|---|---|
| vs AI | **telegraph + startup** = Easy 700+100~160, Normal 500+100~160, Hard 350+100~160ms | AI는 C6 startup **앞에** 별도 예비동작(telegraph)을 둔다. 목표 머리 위치는 telegraph 시작 시점에 고정. 반응형 회피의 "whoa"는 이 모드에서 보장된다. Hard는 반응 여유가 빠듯하므로 PoC로 조정한다 |
| PvP | startup만 (100~160ms) | **반응형 회피는 불가능하다고 명시한다.** 실제 복싱처럼 예측형 회피가 된다. 판정은 방어자 PoseState를 서버 시각으로 환산한 링버퍼에서 active 시작 시각 샘플을 쓰고, 늦게 도착한 샘플을 위해 최대 `REWIND_GRACE = 80ms` 판정을 지연한다(방어자 우선, PoC로 0~120ms 조정) |

**조준 고정 (모든 공격 공통)**: 공격의 목표점은 **공격 시작 시점의 방어자 머리 위치에 고정**되고 이후 추적하지 않는다. AI 공격은 telegraph 시작 시점, 플레이어 공격(vs AI·PvP)은 startup 시작 시점(PvP는 서버가 `input:strike`를 수신해 서버 시각으로 환산한 시점)이 기준이다. 판정은 active 시작 시점의 방어자 머리 구가 고정된 목표점의 글러브 구와 교차하는지로 한다.

**slip hold (연속값으로 정의)**: 판정 창은 `[max(aimLockTime, activeStart − 250ms), activeStart]`이다. **조준 고정 이전 샘플은 제외**하므로 공격 전에 피했다가 돌아온 경우는 인정되지 않는다. 유효 머리 위치는 이 창의 샘플 중 월드 변위(`headX×0.30m`, `headY×0.15m`)가 조준점에서 **유클리드 거리로 가장 먼 단일 샘플**이다(축별 최댓값을 조합하지 않는다). 이 창 안에서 한 번이라도 머리 구가 글러브 구를 벗어나면 회피가 인정된다. 별도의 이산 slip 상태를 전송하지 않으며, 서버(PvP)와 로컬 combat(싱글)이 같은 PoseState 버퍼로 같은 계산을 한다.

### C11. 머리 오프셋 → 월드 변위, 가드 판정
- 히트 판정용 머리 구 변위 = `headX × 0.30m`, `headY × 0.15m`. headX=±1은 캘리브레이션에서 측정한 사용자 최대 slip이다. 머리 구(r 0.13) + 글러브 구(r 0.08) = 0.21m를 벗어나려면 **|headX| ≥ 0.70**이어야 회피가 성공한다(수치는 튜닝 대상).
- 카메라 변위는 별도: `headX × 0.25m`, 임계 감쇠 스프링 ω=12rad/s, 클램프 X ±0.25m / Y ±0.15m. **카메라 감쇠는 판정에 쓰지 않는다**(판정은 비감쇠 PoseState 값).
- **가드**: active 시작 시점 `PoseState.guard ≥ 0.7`이면 `blocked`(MVP는 머리·몸통 모두 막음). 칩 데미지 20%.
- `DefenseState`(C2)는 **로컬 UI/디버그 전용 파생값**이며 네트워크로 보내지 않는다. 네트워크 계약은 `StrikeEvent`와 `PoseState`뿐이다.

### C12. 추적 손실·카메라 오류
- **프레임 단위 규칙**: 어깨 2점 visibility < 0.5이거나 포즈가 미검출된 **그 프레임부터** 판정용 PoseState는 중앙·무방비(`headX=0, headY=0, guard=0`)다. 검출 중인 동안에는 회피 크레딧이 없다.
- 추적 손실(상태) = 위 조건이 **500ms 이상** 지속된 경우. UI 경고와 일시정지 판단에만 쓴다.
- **일시정지 예산**: 온라인 경기에서 플레이어당 추적 손실 PAUSED 누적 30초를 넘으면 FORFEIT. 손실 상태에서는 펀치 이벤트 생성을 멈추고, (위 프레임 단위 규칙대로) **판정용 PoseState는 `headX=0, headY=0, guard=0`(중앙·무방비)으로 전송**한다. 화면에서 이탈한 동작이 회피로 인정되지 않게 하기 위해서다. 마지막 머리 값은 **카메라 연출에만** 유지한다(급격한 시점 튐 방지).
- 싱글: 손실 2초 → 자동 PAUSED + "카메라 앞으로 돌아오세요" 오버레이, 복귀 시 3초 카운트다운 후 재개.
- 온라인: 손실 3초 → PAUSED(연결 끊김과 같은 처리), 20초 초과 → FORFEIT.
- 이벤트 `confidence < 0.4`는 게임이 무시한다(디버그 로그에만 표시).
- 카메라 권한 거부·장치 없음: 웹캠 설정 화면을 통과할 수 없다. **키보드 모드는 싱글 전용**으로 제공하고, 온라인 대전은 웹캠이 필수다.

### C13. 캐릭터 생성 UX·타임아웃·교체
- **T0 스킨은 업로드 직후 항상 먼저 만든다**(클라이언트, 2초 이내). 사용자는 즉시 플레이 가능한 "내 캐릭터"를 갖는다. T1/T2는 백그라운드에서 생성된다.
- 단계별 타임아웃: PREPROCESSING 30s, GENERATING 5min, POSTPROCESSING 2min, RIGGING 2min, VALIDATING 1min, EXPORTING 1min, **전체 10min**. 초과하면 `FAILED{retryable:true}`가 되고 T0가 유지된다.
- 완료되면 토스트 "3D 캐릭터 준비 완료"를 띄우고, **다음 경기 시작(READY 진입) 시 자동 교체**한다(설정에서 끌 수 있음). 경기 중에는 교체하지 않는다.
- 캐릭터 교체는 RESULT→READY 사이에만 허용한다. 싱글은 로컬에서 처리한다. 온라인은 **클라이언트가 RESULT 단계에서 `match:rematch`를 보내기 전에** `player:character {characterId}`를 보내고, 서버는 READY 이전에만 수락한다. READY 이후에 생성이 끝나면 **그다음 경기**에 적용된다.
- 큐 대기(QUEUED)는 전체 10분 타임아웃에 포함하지 않는다. 대신 대기 순번을 표시하고, 대기가 15분을 넘으면 사용자에게 취소를 제안한다. retryable 실패는 **워커가 1회 자동 재시도**하고, 이후 재시도는 사용자 버튼으로만 한다.
- **데모 트릭 조건**: 업로드(0:00) → 캘리브레이션(약 1분) → AI 경기(최대 90초)이므로 약 2.5분 안에 끝나야 한다. 시연용 이미지는 **p50 ≤ 2분**을 목표로 하고, 미완료면 재대결은 T0로 진행한 뒤 사전 생성 캐릭터로 넘어간다.

### C14. 생성 메쉬 정렬과 휴머노이드 판정 (T2/T1/T0 분기)
1. **정렬**: 생성 메쉬를 정면 정사영으로 렌더하고, 그 렌더와 원본 이미지에 MediaPipe Pose를 실행해 2D 관절을 얻는다. 메쉬 단면 중심으로 깊이를 추정해 `mba-humanoid-v1` 관절 위치를 피팅한다. 입력 품질은 A-pose 실루엣 그리기 템플릿으로 끌어올린다.
   - **PoC 측정 항목(P2/P3)**: 생성 메쉬 렌더·만화풍 그림에서 MediaPipe 랜드마크 검출률. 검출률이 낮으면 대체 경로로 **A-pose 그리기 템플릿의 고정 관절 좌표**(템플릿으로 그린 그림은 관절 위치를 이미 안다)를 쓴다. T1+ ≥ 70% 성공 기준은 이 PoC 결과에 따라 재설정한다.
2. **휴머노이드 판정**: 핵심 랜드마크 17개(코·어깨·팔꿈치·손목·엉덩이·무릎·발목 등) 중 visibility ≥ 0.5가 **13개 이상**이고, 팔·다리 길이 비율이 허용 범위(예: 팔/몸통 0.6~1.6) 안이어야 한다.
3. 분기: 판정 통과 + smooth 검증 통과 → **T2**. 판정 통과 + smooth 실패 → **T1 rigid**. **판정 실패(정렬 불가) → T0**. rigid도 정렬이 성공해야만 가능하며 "항상 성공"하지 않는다.
4. 검증기: 테스트 포즈 6종(guard, jab 최대 신전, straight 최대 신전, slip L/R, KO)에서 **최대 엣지 늘어남 비율 ≤ 1.6, 뒤집힌 삼각형 ≤ 2%**(초기값, PoC로 튜닝).
5. Meshy API를 쓰더라도 **메쉬만 사용**하고 위 정렬·바인딩을 똑같이 거친다(Meshy 리그는 공통 스켈레톤이 아니다).

### C15. 애니메이션 리타게팅 (오프라인, TA 담당 W1~W2)
- 소스: **Quaternius UAL(CC0)이 기본**이고 팀이 Blender에서 직접 만든 복싱 클립을 더한다. Mixamo는 Open Question 5가 "허용"으로 결론 날 때만 쓴다.
- Blender에서 소스 리그 → `mba-humanoid-v1` 본 이름 매핑 → 레스트 포즈를 A-pose로 교정 → 클립 베이크 → `animations.glb` 1개로 export한다.
- 런타임 리타게팅은 없다. 모든 캐릭터가 같은 본 이름·레스트 포즈를 가지므로 `AnimationMixer`로 그대로 재생한다. 자동 리거 출력(Mixamo 계열 본 이름)은 바인딩 단계에서 매핑 테이블로 이름을 바꾸고 레스트 포즈를 정규화한다.

### C16. 업로드·개인정보·외부 처리
- 업로드: PNG/JPG/WebP, ≤ 10MB, 짧은 변 ≥ 512px. 권리 확인 체크 필수.
- **MVP 공개 범위는 `private`뿐**이다(경기 상대에게는 표시). 공개 갤러리·`unlisted`는 확장. 상대의 커스텀 캐릭터를 "기본 외형으로 보기"로 숨길 수 있고, 신고 버튼(수동 처리)을 둔다.
- 외부 처리(RunPod, Meshy)를 쓰면 업로드 화면에 "이미지가 외부 GPU/API로 전송됨"을 고지하고 동의를 받는다. **거부하면** 팀 로컬 GPU 워커가 있을 때만 그쪽으로 보내고, 없으면 T0 스킨만 제공한다.
- 보존: 업로드 원본·중간 산출물은 작업 완료 30일 뒤 삭제한다. 최종 캐릭터는 사용자가 지울 때까지 보존한다. "내 데이터 삭제"는 게스트 토큰 단위로 처리한다.

### C17. 경기 경계 규칙
- TIME_UP에서 HP 비율이 같으면 **무승부**.
- 피격 경직(300ms) 중 펀치 입력은 서버가 거부하고(`strike:rejected`) 클라이언트 예측 애니메이션을 취소한다.
- 동시 명중(같은 서버 틱 active)은 **양쪽 모두 적용**(상호 타격).
- 싱글: 같은 규칙을 브라우저의 `packages/combat`가 고정 60Hz 시뮬레이션 틱으로 실행한다. 경직 중 입력은 로컬에서 무시하고 예측 애니메이션도 시작하지 않는다. 동시 명중 기준은 같은 시뮬레이션 틱이다.

## Success Criteria

- 핵심 시연 경로 5단계가 **연속 3회 리허설 무중단**.
- 잽/스트레이트 F1 ≥ 0.85, 가드 F1 ≥ 0.9, 좌우 회피 F1 ≥ 0.85 (팀 녹화 데이터셋, 5인 이상).
- 오인식 펀치(가만히 있을 때) ≤ 1회/분.
- 입력→화면 반응 p50 ≤ 150ms, 게임 FPS p95 프레임타임 ≤ 25ms(내장 GPU 노트북 기준 30fps 이상).

### R3-1 — consistency (blocking)

**Problem**

> The slip-hold window is the last 250ms before active start, but in PvP (and player strikes) startup is only 100-160ms, so the window reaches 90-150ms before the aim-lock moment. A defender who was slipped before the strike began, returned to center, and is sitting exactly on the locked aim point at both lock time and active start is still credited with a dodge because a pre-attack sample is far from the aim point. Continuous weaving with a period under ~250ms therefore makes a PvP defender effectively unhittable. This contradicts the new aim-lock rule ('judgment is whether the head sphere at active start intersects the locked target') and C6's 'defender state at active start'.

**Remedy**
