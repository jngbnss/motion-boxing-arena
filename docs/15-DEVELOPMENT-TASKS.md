# 15. 개발 작업 분해, 설계 결론, 검토 체크리스트

> 상태: 계획. 작업 ID는 GitHub Issue 제목 접두어로 사용한다(예: `[M1-03] 펀치 FSM`).

## 1. 설계 결론 (요구사항 20의 13개 질문)

| # | 질문 | 답 |
|---|---|---|
| 1 | 기술적으로 구현 가능한가? | **가능하다. 단, 범위를 계층화해야 한다.** 핵심 경로(웹캠 → 이벤트 → 1인칭 복싱 → AI 상대)는 검증된 기술(MediaPipe, Three.js)만으로 8주 안에 충분히 가능하다. 2D→3D→리깅은 "항상 성공하는 T0 스킨"이 받쳐줄 때만 일정 위험이 없다. |
| 2 | 쉬운 것 / 어려운 것 | 쉬움: 3D 경기장·HUD, 키보드 게임, 해석적 타격 판정, FSM AI, Colyseus 룸, 게스트 API. 중간: 캘리브레이션·가드·좌우 회피 인식, 서버 권한 판정, 작업 큐. 어려움: **정면 펀치 인식(깊이)**, **AI 메쉬 자동 리깅 품질**, 지연 하에서 회피 판정의 공정성, 생성 GPU 운영. |
| 3 | 가장 큰 병목 5개 | ① 단일 RGB 카메라의 정면 펀치 깊이 모호성 ② AI 메쉬(비매니폴드·비대칭)의 스키닝 품질 ③ 이미지→3D GPU(24GB급)와 생성 시간 ④ 입력→화면 지연(카메라 33ms + 추론 + 판정 + 렌더)과 네트워크 RTT의 합 ⑤ 7명 병렬 개발의 통합 비용 |
| 4 | 활용할 오픈소스 | Three.js(MIT), @mediapipe/tasks-vision(Apache-2.0), Colyseus(MIT), Rapier(Apache-2.0, 연출용), TRELLIS/TRELLIS.2(MIT, 의존성 확인)·SPAR3D(Stability Community)·TripoSR(MIT) 중 PoC 선정, Make-It-Animatable/UniRig(MIT), Blender(GPL, 별도 프로세스), rembg/BiRefNet, Quaternius 애니메이션(CC0). 상세: [14](14-OPEN-SOURCE-LICENSES.md) |
| 5 | AI 모델이 실제로 필요한 곳 | 포즈 추정, 배경 제거, 이미지→3D, (선택) 자동 리깅 가중치. 그 외(동작 분류 v1, 타격 판정, 게임 AI, 네트워크)는 알고리즘·규칙이다. |
| 6 | 직접 학습이 필요한가? | **MVP에는 필요 없다.** 동작 분류에서 규칙 기반 F1이 목표(0.85)에 못 미칠 때만 녹화 데이터로 소형 분류기(GBDT/1D-CNN)를 학습한다. 3D 생성·리깅 모델의 재학습은 범위 밖. |
| 7 | 2D→3D→리깅→게임 적용 가능? | **휴머노이드 정면 전신 이미지에 한해 조건부 가능(PoC 필요).** 공통 스켈레톤 + smooth/rigid 자동 강등 + T0 스킨으로 "항상 무언가는 게임에 들어간다"를 보장한다. 임의 이미지에서 고품질 관절 변형은 보장할 수 없다. |
| 8 | 웹캠만으로 1인칭 모션 복싱 가능? | **가능하다.** 단 "실제 동작 복제"가 아니라 "동작 이벤트 + 머리 오프셋" 수준이다. 잽/스트레이트/가드/좌우 회피는 규칙 기반으로 충분히 안정화할 수 있고, 훅·어퍼컷·숙이기는 확장으로 둔다. 힘·거리 측정은 하지 않는다. |
| 9 | 온라인 1:1 핵심 난제 | 회피가 실시간 머리 움직임이라 **지연 하에서 "피했는데 맞았다"** 가 생기는 문제. 펀치 예비동작(100~160ms)으로 RTT/2를 가리고, 방어자 상태 기준(방어자 우선) 서버 판정으로 해결한다. 부정 입력은 완전 차단 불가(카메라 진위 증명 불가) → 랭크 모드 제외. |
| 10 | 8주 필수 범위 | MVP 0 + MVP 1 + T0 스킨 + 측정 보고서. 즉 **웹캠으로 AI 상대와 1경기 완주 + 결과 + 지표**. 온라인과 3D 생성은 W2·W5 게이트로 시연 포함 여부 결정. |
| 11 | 포트폴리오 강조점 | ① 녹화 리플레이 기반 동작 인식 평가 파이프라인(P/R/F1, 개선 전후) ② 입력→화면 지연 계측·최적화 ③ 이미지→3D 모델 비교 선정과 실패율 기반 단계 강등 설계 ④ 클라/서버 공유 결정적 전투 로직으로 판정 불일치 제거 ⑤ 라이선스 검토로 Hunyuan3D 배제 결정 |
| 12 | 첫 검증 프로토타입 | **P1: 브라우저 한 페이지에서 웹캠 → Pose lite → 잽/스트레이트/가드/좌우 회피를 디버그 오버레이에 실시간 표시 + 랜드마크 JSONL 녹화.** 게임 전체의 성패가 여기 달려 있고 1인이 3~4일이면 만든다. |
| 13 | 기능별 개발 우선순위 | 아래 §3의 P0 → P1 → P2 순. |

## 4. 설계 검토 체크리스트

개발 착수 전 팀 회의에서 항목별로 담당자가 "예"라고 답할 수 있어야 한다.

### 범위·일정
- [ ] 핵심 시연 경로 5단계가 MVP 0+1만으로 성립함을 모두 이해했는가?
- [ ] W2 Go/No-Go, W5 I-2의 판정 기준과 축소 시나리오에 동의했는가?
- [ ] W7 수요일 기능 동결에 동의했는가?
- [ ] 역할 7개에 실제 사람이 배정되었고, MO는 겸임하지 않는가?

### 계약
- [ ] C2 행동 이벤트로 게임이 필요한 모든 입력을 표현할 수 있는가(키보드·리플레이 포함)?
- [ ] C3 공통 스켈레톤 본 이름과 레스트 포즈를 TA·GC·AI가 같은 파일로 공유하는가?
- [ ] C6 전투 상수를 싱글(브라우저)과 서버가 같은 패키지에서 읽는가?
- [ ] C7 메시지마다 서버 검증 규칙이 정의되어 있는가([08](08-API-DESIGN.md))?
- [ ] C9 작업 단계마다 산출물 경로와 재시도 가능 여부가 정의되어 있는가?

### 모션
- [ ] 펀치 인식이 "실제 거리·힘"에 의존하지 않는가?
- [ ] 캘리브레이션 없이 플레이를 시작할 수 없게 막았는가?
- [ ] 정지 상태 오인식률 측정 방법이 있는가?
- [ ] 리플레이 입력으로 웹캠 없이 게임을 돌릴 수 있는가?

### 판정·멀티
- [ ] 히트 볼륨이 캐릭터 메쉬와 무관한가?
- [ ] 서버만 HP를 바꾸는가? 클라이언트는 자기 애니메이션만 예측하는가?
- [ ] 지연 100/200ms 시뮬레이션 테스트가 계획되어 있는가?

### AI 3D
- [ ] Hunyuan3D 미사용 결정과 근거(지역 제한)를 모두 알고 있는가?
- [ ] GPU 확보 경로(팀 GPU / RunPod / Meshy)가 1개 이상 확정되었는가?
- [ ] 생성 실패 시 사용자가 항상 T0 스킨을 받는가?
- [ ] 업로드 시 권리 확인과 비공개 기본값이 있는가?

### 운영·안전
- [ ] 웹캠 영상이 어떤 네트워크 요청에도 포함되지 않음을 코드 리뷰 항목으로 두었는가?
- [ ] HTTPS 환경에서 웹캠 테스트를 했는가?
